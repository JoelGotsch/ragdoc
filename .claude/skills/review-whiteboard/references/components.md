# Page components

A review is one `index.html` built from `assets/template.html`. Prose is hand-written; everything
bound to source is declared with `data-*` attributes and generated by `scripts/resolve.py`, so a
review never carries a line number or file list that was typed by hand.

## Anchors

An anchor names a line range on one side of the pinned change:

```
head/src/ragdoc/pipeline/sync.py#L92-L107
base/src/ragdoc/pipeline/vectorstore.py#L147
```

`head` and `base` resolve to the shas in `review.json` (a `worktree` head reads the working
copy). `resolve.py` verifies every anchor in the page and prints its first and last line; read
that output and fix any anchor whose lines are not the ones you meant. Never widen a range to
"make it resolve".

## Source link (inline)

```html
<a class="src" data-source="head/src/ragdoc/llm.py#L285-L300"><code>without_sdk_retries</code></a>
```

`resolve.py` sets `href` to the GitHub blob URL at the pinned sha (or `#` when the repository has
no GitHub remote). Use it for every function or line you name in prose.

## Code peek

```html
<figure class="peek" data-source="head/src/ragdoc/pipeline/sync.py#L92-L107"
        data-caption="Why this range matters, one sentence."></figure>
```

The body (path, line label, side badge, numbered code, italic note) is generated. Keep a peek
under 60 lines; `resolve.py` warns above that. Peeks are for contracts and invariants the reader
must see verbatim — a protocol, a validator, a guard — not for walking whole functions.

## Diagram figure

```html
<figure class="diagram" data-diagram="sync-run" data-type="sequence">
  <figcaption>Sequence · run() on one updated source</figcaption>
  <div class="diagram-container">
    <svg viewBox="0 0 1120 620" style="min-width:1120px" role="img"
         aria-labelledby="sync-run-title sync-run-desc" xmlns="http://www.w3.org/2000/svg">
      <title id="sync-run-title">…</title>
      <desc id="sync-run-desc">…</desc>
      <defs>…ids prefixed with sync-run-…</defs>
      …
    </svg>
  </div>
</figure>
```

Rules the checker enforces: `data-type` is `sequence`, `flow` or `call-stack-diff`; the
`aria-labelledby` value is exactly `<slug>-title <slug>-desc`; the viewBox is on the 4px grid and
the inline `min-width` equals its width; every id inside the SVG is prefixed with the slug;
no diagonal `<line>` (use elbow paths). Element groups carry `data-k="actor|msg|node|edge|frame"`
so budgets can be counted, and `data-source` where a step maps to code (verified like any anchor).
`export_diagrams.py` writes `<slug>.svg` next to the page and adds the download link to the
figcaption. See `diagrams.md` and `diagram-call-stack-diff.md` for the drawing rules.

## Callout

```html
<aside class="callout callout-warning">
  <p class="callout-title">What is and is not guaranteed</p>
  <ul>…</ul>
</aside>
```

Variants: `callout-info` (default look), `callout-warning`, `callout-danger`, `callout-success`.
One title line, then prose or a list. At most one callout per section unless the section is a
list of guarantees.

## Collapsible subsection

```html
<details class="sub" open>
  <summary>1 · Pipeline split by boundary</summary>
  <div class="sub-body prose">…</div>
</details>
```

Use these in the Implementation section, one per design thread, numbered in reading order.
Leave the first one `open`.

## File lens

```html
<details class="lens" open>
  <summary>Sync engine: SyncEngine, ChangeSet, sync pipelines <span class="lens-stat"></span></summary>
  <p class="lens-note">Optional one-line note, e.g. "mostly line-ending churn".</p>
  <ul class="lens-files" data-files="src/ragdoc/pipeline/sync.py src/ragdoc/pipeline/vectorstore.py tests/pipeline/**"></ul>
</details>
```

`data-files` is a space-separated list of exact paths or globs (`dir/**` any depth, `*.py` one
segment, `dir/` prefix). `resolve.py` fills the list from `git diff --numstat` with per-file
`+added −deleted` and a link to the file's diff on GitHub, fills the `lens-stat`, warns on a file
claimed by two lenses, and lists every unclaimed file under `<ul class="uncategorized" data-auto>`.
A review is not finished while that list is non-empty: `check_review.py` fails on it.

Order lenses the way the reader should go: non-implementation first (tests, docs, config,
renames, formatting churn), then implementation grouped by design thread in reading order.

## Header placeholders

`{{TITLE}}`, `{{REPO_NAME}}`, `{{HEAD_SHA}}` and the block between `<!-- meta:start -->` and
`<!-- meta:end -->` are filled by `new_review.py` and refreshed by `--retarget`. Do not edit the
meta block by hand; `[TODO …]` markers and `{{…}}` placeholders fail the checker.
